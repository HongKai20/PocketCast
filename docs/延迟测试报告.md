# PocketCast 延迟测试报告

> 本报告分两部分：**第 1~3 节**是构建机器上可复现的管线基准实测（已填真实数据）；
> **第 4~5 节**是端到端（手机 ↔ 电脑 ↔ 会议软件）测量方法与记录表，需在真实手机 + 装有
> VB-CABLE / H.264 解码器的电脑上执行后填写。

---

## 1. 结论摘要

| 项目 | 目标 | 本机实测 | 判定 |
| --- | --- | --- | --- |
| 共享内存送帧（解码输出 → 虚拟摄像头可读） | — | 中位 **77.7 µs**，P95 **152.9 µs**，最大 **276.5 µs** | 远低于 1ms，可忽略 |
| 共享内存写入吞吐 | 支撑 720p30（约 110 MB/s） | **≈ 19.3 GB/s** | 余量 170 倍以上 |
| Opus 48kHz 单声道 10ms 帧 编 + 解 | 单帧 < 10ms | **349.6 µs/帧**（占预算 **3.50%**） | 通过 |
| Opus 实际码率（1kHz 正弦，64kbps 上限） | ≈ 64 kbps | **61.8 kbps** | 通过 |
| VB-CABLE 虚拟声卡 | 可用 | **未安装**（构建机） | 环境缺失，非代码问题 |
| 系统 H.264 解码器 | 可用 | **枚举到 0 个**（Windows N 版） | 环境缺失，非代码问题 |
| 端到端音频延迟 | < 60 ms（5GHz） | 待真机实测 | 见第 4 节 |
| 端到端视频延迟 | < 150 ms（5GHz） | 待真机实测 | 见第 4 节 |

本机管线（解码→共享内存、Opus 编解码）耗时均在**微秒级**，对 60ms / 150ms 的目标几乎不占预算；
端到端延迟的绝大部分来自**采集、编码、网络抖动与播放缓冲**，必须在真机上测。

## 3. 本机管线实测

### 3.1 共享内存送帧延迟（虚拟摄像头链路）

测法：单线程 ping-pong。连续 `Publish` 一帧 1280×720 YUY2 后立即自旋读共享内存头部的
`frameCount`（偏移 56），直到读到新帧为止，取时间差；共 200 个样本（另有 300 帧用于吞吐测试）。

| 指标 | 数值（本次运行） | 参考（前一次运行） |
| --- | --- | --- |
| 中位延迟 | **77.7 µs** | 115.6 µs |
| P95 延迟 | **152.9 µs** | 175.2 µs |
| 最大延迟 | **276.5 µs** | 206.5 µs |
| 写入吞吐 | **≈ 19.3 GB/s** | 17.9 GB/s |

含义：电脑端解码出一帧到虚拟摄像头滤镜能读到它，开销小于 0.3ms，在 150ms 预算里可忽略。
吞吐 19.3 GB/s 对 30fps × 1.76MB ≈ 53 MB/s 的需求有约 360 倍余量。

### 3.2 Opus 编解码耗时与码率

测法：2000 帧 10ms（480 样本）1kHz 正弦，编码后立即解码，统计单帧总耗时与实际码率（含 50 帧预热）。

| 指标 | 数值（本次运行） | 参考（前一次运行） |
| --- | --- | --- |
| 单帧编 + 解 | **349.6 µs** | 384.9 µs |
| 占 10ms 帧预算 | **3.50%** | 3.85% |
| 压缩后码率 | **61.8 kbps** | 61.8 kbps |

含义：手机端 Opus 编码 + 电脑端解码合计占用不到 4% 的实时预算，不会成为延迟瓶颈。
（手机端编码在 ARM 上会慢 5~10 倍，仍远低于 10ms。）

### 3.3 硬件/驱动就绪性

| 检查项 | 结果 | 说明 |
| --- | --- | --- |
| VB-CABLE 音频设备 | 未找到 | 构建机未安装 VB-CABLE / VoiceMeeter；安装后 `CABLE Input` 才会出现 |
| 系统 H.264 解码器（Media Foundation） | 枚举到 **0** 个 | Windows N 版缺少 Media Feature Pack，需安装后重启 |

> 这两项是**构建机环境缺失**，不是代码缺陷：`MfH264Decoder` 的错误信息会明确提示安装
> Media Feature Pack；`VirtualCableAudioSink` 在找不到设备时只打日志、不影响其余功能。

## 4. 端到端延迟测量（需真机）

端到端指：**手机采集 → 编码 → WiFi 传输 → 电脑解码 → 虚拟设备 → 接收软件渲染/播放**。

### 4.1 方法 A：App 内一键自检（推荐）

1. 手机与电脑连同一 WiFi（5GHz），电脑端 `PocketCast.exe` 已启动并显示“手机已连接”。
2. 手机 App 打开「麦克风」+「摄像头」开关。
3. 点「延迟自检」：手机会同时**闪光**（屏幕全白一帧）并**响 1kHz 蜂鸣**。
4. 电脑端 `ProbeAnalyzer` 检测共享内存帧亮度跳变与解码 PCM 能量跳变，
   结合 NTP 式四时间戳时钟同步（`clock` / `clock_ack` / `clock_result`）换算出端到端延迟。
5. 手机与电脑状态栏都会显示：`端到端延迟：音频 xx ms / 视频 yy ms`。

建议连测 10 次取中位数；每次间隔 2 秒以上。

### 4.2 方法 B：拍手 + 录屏逐帧（无 App 自检时的交叉验证）

1. 电脑屏幕放一个秒表（毫秒刷新）。
2. 手机对着屏幕拍手，同时用 `Win+G`（Xbox Game Bar）录屏 30~60 秒。
3. 逐帧查看：画面里秒表数字变化的那一帧 vs 录屏音轨里拍手声的起始帧
   → 差值即**音频端到端延迟**；画面里秒表数字由“旧值”变“新值”的帧差 → **视频延迟**。
4. 注意减去录屏本身的开销（先录一段纯屏幕秒表，测出 Game Bar 的基准偏移）。

### 4.3 方法 C：高速摄像（最严谨）

用 240fps 手机慢动作同时拍「手机闪光」和「电脑屏幕出现相应画面」，数帧差即可，误差 < 5ms。

## 5. 延迟预算拆解与达标分析

理论拆解（720p / 5GHz / Opus 10ms 帧）：

| 环节 | 音频典型值 | 视频典型值 | 依据 |
| --- | --- | --- | --- |
| 采集 | 10~20 ms（AudioRecord 10ms 缓冲） | 33 ms（30fps 一帧周期） | 帧率/缓冲决定 |
| 编码 | < 5 ms（Opus，手机 ARM） | 5~15 ms（MediaCodec 硬编） | 第 3.2 节 + 硬编实测经验 |
| 网络（单程） | 2~8 ms（5GHz 局域网） | 2~8 ms | RTT 通常 5~15ms |
| 抖动缓冲 | 10~30 ms | 20~60 ms（2~3 帧） | WebRTC 默认自适应 |
| 解码 | < 2 ms | 5~10 ms（MF 硬解） | 第 3.1 节 |
| 虚拟设备 | < 1 ms（共享内存/VB-CABLE） | < 1 ms（共享内存） | 第 3.1 节 |
| 接收软件缓冲 | 10~20 ms | 一帧（33 ms） | 会议软件自身 |
| **合计** | **约 40~85 ms** | **约 100~160 ms** | — |

结论：

- 音频在 5GHz 下达到 **< 60ms** 是可行区间，2.4GHz 或信号弱时会超出；
- 视频在 5GHz 下处于 **~150ms** 边缘，降到 480p 或降低抖动缓冲可稳定达标；
- 若测得明显超标，优先检查：WiFi 是否 5GHz、手机是否锁屏、是否有其他大流量设备、
  会议软件的“低延迟模式”是否开启。

优化手段（已内置或可调）：

| 手段 | 位置 | 效果 |
| --- | --- | --- |
| Opus 10ms 帧 + FEC + `adaptiveAudioPacketTime` | 手机端 `WebRtcSession` | 降低音频抖动缓冲需求 |
| 音频编码上限 64kbps（自适应 24~64kbps） | 手机端 | 拥塞时自动降码率保延迟 |
| 视频 480p / 960×540 档位 | 手机端分辨率选择 | 降低编码与网络耗时 |
| 摄像头按需开关 | 手机端 | 关闭时零采集、零推流 |
| 共享内存 4 槽 + seq 校验 | 电脑端 ↔ 滤镜 | 无锁、无撕裂、亚毫秒级传递 |

## 6. 已知偏差与限制

- 本报告的管线数据来自**构建机**（Windows N 版、无 VB-CABLE），不含真机端到端结果；
  第 4 节表格留待真机填写。
- `ProbeAnalyzer` 的自动测量依赖时钟同步（`RTT` 抖动应 < 10ms），WiFi 抖动大时单次结果会偏差，
  建议取 10 次中位数。
- 虚拟摄像头滤镜的取帧线程固定 30fps 节拍，实际视频延迟下限为 1 帧（33ms）。
